# 물리적 접근 제어 — AI가 자발적으로 따르는 규칙이 아닌 실행 경계

## 권장 구성

Git은 상태 확인에 필요한 읽기 전용 조회만 제공한다. 실제 Git directory/common directory/index/refs/config와 사용자 Git 설정은 쓰기 차단하고, 원격 쓰기 자격증명을 제공하지 않는다. `.git`만 보호해도 checkout/restore/clean처럼 작업 파일을 바꾸는 명령까지 막히지는 않으므로, 에이전트의 Git 실행은 신뢰된 읽기 전용 조회 인터페이스로 제한해야 한다. 임의 셸에 일반 Git 실행권을 그대로 주고 완전 차단됐다고 주장하지 않는다. 외부 도구·직접 파일 쓰기 우회도 같은 권한 경계에 포함한다. 소스 사본 준비·clone/worktree·branch 생성·hook/CI 설정은 사용자가 직접 수행하며, AI는 실행하거나 권한을 요청하지 않는다.

가장 명확한 방법은 비밀이 없는 별도 VM/격리 CI 작업공간이다. 사용자 호스트에서 실제 SDV testbed와 Google 자격증명을 관리하고, AI는 합성 fixture와 제한된 코드 사본만 사용한다. 단순히 폴더를 다른 위치로 옮기거나 파일을 숨기는 것으로는 부족하다.

| 영역                                             | 에이전트 권한                | 운영자 작업                                                  |
| ------------------------------------------------ | ---------------------------- | ------------------------------------------------------------ |
| 작업 소스·신규 테스트·임시 빌드 경로             | 승인된 디렉터리만 읽기/쓰기  | 작업 범위 사본과 출력 위치 준비                              |
| 공개 명세·적용 완료 migration                    | 읽기 전용                    | 부모 디렉터리의 삭제/교체 경로까지 보호                      |
| 호스트 원본 저장소 Git 메타데이터                | 쓰기 불가                    | 읽기 전용 상태 조회 또는 제한된 검사 서비스 제공             |
| google-oauth.local.env, secrets, 사용자 자격증명 | 읽기·열거·쓰기 모두 불가     | VM에 미마운트; 호스트 별도 실행 계정의 권한으로 관리         |
| docs/workmd 및 구현 제외 자료                    | 미제공/접근 불가             | 필요한 승인된 작업 요약만 공개                               |
| 실제 DB/Kafka/Google/Ollama/testbed 제어         | 기본 접근 불가               | 일반 구현 환경에 토큰·포트·서비스 관리권한 미제공            |
| 합성 테스트 DB/Kafka                             | 격리 환경에서만 허용         | 폐기 가능한 독립 인스턴스/네트워크 구성                      |
| 실제 호스트 Docker 엔진/관리 named pipe          | 접근 불가                    | 테스트용 VM 내부 엔진만 제공하거나 신뢰된 테스트 runner 사용 |
| 하네스 정책·CI 문지기·접근 설정                  | 일반 구현 작업에서 수정 불가 | 별도 검토 후 고정 버전 배포                                  |

새 migration을 추가하면서 과거 migration만 보호해야 한다. 폴더 전체를 무조건 쓰기 금지하면 신규 파일도 만들지 못하므로, 승인된 기존 파일 목록에 보호 ACL을 적용하거나 별도 staging 위치에서 운영자가 새 파일을 가져오는 방식으로 설계한다. 파일 쓰기 금지만으로 부모 폴더에서 삭제/교체가 가능한 구성이 아닌지 확인한다.

## Windows 적용 단계 — 아직 실행하지 않은 운영 계획

1. 현재 하네스/진행 중인 보안 교정 작업을 분리하고, 운영자가 어떤 경로를 agent에 제공할지 승인한다.
2. 전용 비관리자 실행 계정 또는 별도 VM을 만든다. 사용자의 브라우저 로그인·Credential Manager·SSH agent·Git 자격증명·클라우드 로그인은 전달하지 않는다.
3. 허용된 소스와 공개 명세만 작업공간에 제공한다. 비밀, 개인 Drive 자료, 런타임 로그, DB dump와 금지 문서는 제공하지 않는다. Git 이력에도 비밀이 있을 수 있으므로, 필요하다면 이력이 없는 검토된 사본과 별도의 읽기 전용 상태 조회를 제공한다.
4. OS 파일 권한/VM mount 정책으로 읽기·쓰기·열거를 구분한다. agent 계정이 ACL 소유권 변경, 관리자 상승, 원본 저장소나 보호 디렉터리 교체를 할 수 없어야 한다. 현재 사용자 계정 전체에 광범위한 deny를 걸지 않는다.
5. 기본 네트워크 차단 후 합성 테스트 endpoints만 허용한다. VM에서 호스트 gateway를 통해 실제 localhost 서비스에 접근하는 우회도 차단한다. 패키지 설치는 별도 준비 단계에서 하고 테스트 실행에는 실제 서비스 비밀을 전달하지 않는다.
6. Codex/IDE의 사용 가능한 sandbox와 승인 정책을 이 범위에 맞춘다. 승인 거부 상태에서 더 넓은 경로 접근이 실패하는지 확인한다. 정확한 설정 키는 설치된 버전의 공식 문서로 확인한다. `workspace-write`만 선택했다고 비밀 read가 차단됐다고 간주하지 않는다.
7. 브라우저·컴퓨터 제어·연결 도구·다른 task로의 메시지/위임도 별도 범위를 검토한다. shell ACL만으로 호스트 로그인 브라우저의 정보나 연결 도구 권한이 제한되지는 않는다. offline 구현 세션에서는 불필요한 도구를 제공하지 않는다.
8. CI required check와 하네스 정책을 운영자가 설치한다. AI가 만든 결과 JSON 자체가 아니라, 신뢰된 CI 실행의 성공 여부를 병합 조건으로 삼는다.

## 실제 비밀 대신 가짜 보호 대상을 이용한 검증

각 확인은 에이전트와 동일 실행 계정·도구 경로에서 한다. 진짜 비밀 파일을 열어보는 검증은 하지 않는다.

- 보호 디렉터리의 가짜 문자열 파일: PowerShell, Node, 자식 프로세스 모두 읽기 실패.
- 가짜 Git 메타데이터/기존 migration: 쓰기뿐 아니라 삭제 후 동일 이름 재생성·이름 변경도 실패.
- 허용 소스 디렉터리: 파일 생성·변경·테스트 산출물 쓰기는 성공.
- 테스트용 symlink/junction: 보호 경로를 우회하는 읽기·쓰기 실패.
- 가짜 금지 네트워크 endpoint: 접속 실패. 합성 테스트 endpoint만 성공.
- 사용자 자격증명·호스트 Docker control·관리자 상승 경로가 환경에 노출되지 않았는지 운영자가 확인.
- sandbox 권한 확장 요청을 거절한 상태에서 동일 작업이 다른 도구로 자동 우회되지 않는지 확인.

이를 통과해야 “물리적으로 차단됐다”고 기록한다. 이 문서는 설계일 뿐 해당 검증을 실행했다는 증거가 아니다.

## 같은 PC/같은 계정만 사용할 때의 한계

전용 VM/실행 계정 없이 IDE 숨김 설정, gitignore, 쉘 명령 문자열 차단만 사용하면 우회 가능한 안내에 가깝다. 사용자가 준 전체 관리자 권한과 임의 셸 실행을 유지하면서 프롬프트만으로 모든 Git 변경·비밀 읽기를 막는 구성은 제안하지 않는다.

CI에서 테스트 코드는 임의 코드로 실행된다. 테스트를 허용했다는 이유로 실제 운영 Docker/DB 권한을 주어서는 안 된다. 격리, 최소 권한, 외부 병합 통제를 함께 적용해야 한다.
