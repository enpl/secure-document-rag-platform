**보류된 세분화(사용자 결정, 이번 범위 밖).** 429/일시 장애가 아닌 실패(인증 실패 401, 잘못된/만료된 Google Change 페이지 Token 400 등)는 기존 `SourceSyncException.Reason`(NOT_FOUND/ACCESS_UNKNOWN/FAILED 3종)을 그대로 재사용해 동일한 지수 Backoff로 처리한다 - "인증 실패라서 재연결이 필요하다"와 "일시적 서버 오류다"를 스케줄러가 서로 다르게 안내하지는 못한다. 더 정밀한 구분(`GoogleApiException.Category`/`SourceSyncException.Reason` 확장)은 `GoogleDriveConnector.toSyncException` 등 기존 exhaustive switch 여러 곳을 함께 고쳐야 하는 더 넓은 범위라 사용자가 이번에는 보류를 선택했다. 실제 backend 재시작 후 실제 자동 증분 성공/색인 갱신은 이 세션에서 검증하지 않았다(오프라인 구현·회귀만 완료).

**2026-09-18 자동 증분 동기화 다중 사용자 안전성 결함 3건 교정(`feat/mvp-frontend-polish` Phase A, 사용자 승인).** 위 구현이 남긴 세 결함을 최소 수정했다: (1) 대상 조회(`findDueForAutoIncrementalSync`)가 Lease가 지난(만료된) `RUNNING`만 통과시키도록 좁혀, 프로세스 중단으로 남은 만료 Run이 기존 `SyncRunLifecycle.beginRun`의 회수(`reapAbandoned`) 경로 자체에 도달하지 못하고 영원히 막히던 문제를 해소했다(새 회수 로직 없음, 기존 V008/V009 그대로 재사용). (2) `AutoIncrementalSyncScheduler.processOne`이 `syncChanges`가 반환한 실제 `SyncRunEntity.status`를 확인해 `COMPLETED`일 때만 성공 기록하고, `PARTIAL_FAILURE`/`ABANDONED`는 예외와 동일한 지수 Backoff로 처리한다(이전엔 예외만 없으면 무조건 성공 기록). (3) `source_sync_cursors.claim_token`(신규 Migration V015, UUID 하나만 추가)으로 완료 기록에 Claim 소유권 Fencing을 적용해, 오래 걸린 이전 Tick의 뒤늦은 완료 보고가 그 사이 새로 Claim된 `next_check_at`/`consecutive_failures`를 덮어쓰지 못하게 했다(기존 `outbox_events.claim_token`과 동일 패턴 재사용). 실제 Testcontainers PostgreSQL 기준 신규 6개 테스트(만료 RUNNING 포함/건강한 RUNNING 계속 제외, 회수된 Run에 대한 실제 두 번째 동시 시도 거부, PARTIAL_FAILURE의 Backoff 처리, 오래된 성공/실패 보고 무시 2건)로 검증했고, 기존 27개 자동 동기화 테스트 + 관련 Sync/Event/Source/Config 회귀 전부 무영향을 확인했다.

**신규 발견(미차단, 보류) - PARTIAL_FAILURE 초기 동기화의 지원되는 복구 경로 없음.** 운영 안내를 실제 코드와 대조하는 과정에서 확인했다: `source_sync_cursors` 행이 이미 존재하면 `POST /api/sources/{id}/sync`(`SourceSyncService.sync`)는 항상 `INCREMENTAL`로만 진입한다(`beginAutoRun`이 Cursor 유무로만 FULL/INCREMENTAL을 고른다) - 최초 FULL Sync가 `PARTIAL_FAILURE`로 남아 있어도 수동 `/sync`를 아무리 다시 눌러도 새 FULL Run은 시작되지 않는다. 새 FULL Run을 시작하는 유일한 Method(`SourceSyncService.startInitialSync`)는 어떤 Controller에도 연결되어 있지 않다 - 즉 **현재 이런 연결을 다시 COMPLETED로 되돌리는 지원되는 방법이 없다.** 핵심 기능을 차단하지 않고(자동/수동 증분은 여전히 정상 동작) 새 정책 결정(예: 명시적 재스캔 API를 추가할지, 추가한다면 누가 언제 호출할 수 있는지)이 필요한 범위라 이번에는 구현하지 않고 여기 기록만 남긴다 - 다음 작업에서 사용자가 필요성을 확인하면 우선순위를 정해 진행한다.

**2026-09-18 프론트엔드 업무용 SaaS 디자인 고급화(`feat/mvp-frontend-polish` Phase B, 사용자 승인).** 화면 구조·탐색·업무 흐름과 파란색 브랜드는 그대로 두고, 단일 전역 스타일시트(`frontend/src/index.css`)의 디자인 토큰과 공통 클래스(`.card`/`.btn`/`.input`/`.pill`/`.status-banner`/`.file-table`/`.source-row` 등 - 모든 화면이 재사용하는 어휘)만 재정의했다. 콘텐츠 배경(`--canvas`)을 카드 표면(`--surface`)과 분리해 표면 구분을 명확히 하고, radius를 20~24px(알약형)에서 8~12px로 낮췄으며, 간격·타이포그래피 위계(h1/h2/h3, `.form-label`)를 정리했다. `recipient-chip`/`recipient-options`가 토큰 대신 하드코딩 색상을 써서 dark mode에서 깨지던 실제 결함을 발견해 토큰으로 교체했다. 상태 표현에 `--warning`(amber) 등급을 새로 추가해(`status-banner--warning`, `pill--warning`) `ragOutcomeSeverity`(신규, `api/ragAssistant.ts`, 기존 `status` 값만 재분류 - 새 서버 값 없음)로 답변 성공/부분/거부를, `SourceSyncPanel`에서 PARTIAL_FAILURE/RUNNING(경고)과 FAILED/ABANDONED(오류)를 구분했다 - 기존 값만 재사용하고 새 상태·API는 추가하지 않았다. `prefers-reduced-motion: reduce`를 전역(`*`)에 적용해 모든 Transition을 존중하게 했다. 새 격리 Playwright 진입점 `frontend/e2e/visual.config.ts` + `e2e/visual/`(기존 `verify-no-e2e-leak.mjs`/`verify-preview-isolation.mjs`와 동일한 "수동 실행, 어떤 Gate에도 연결 안 함" 관례)로 대표 화면 11장을 1440×900/1024×600/390×844, light/dark, 200% 확대, 긴 한국어 파일명, 빈/실패/부분 결과 상태로 캡처해(`e2e/.report/design-polish/`, 기존 gitignore 범위) 직접 확인했다 - Mobile Drawer 스크린샷에서 CSS Transition 완료 전에 캡처해 실제로는 정상인 화면이 깨진 것처럼 보였던 것을 재확인으로 구분했다(실제 결함 아님). 기존 필수 7개 시나리오(`npm run test:e2e:harness`, `admin-conflict-reload`/`desktop-navigation`/`inert-output-no-external-resources`/`login-bootstrap`/`long-file-list-and-sticky-controls`/`mobile-focus-and-overlay`/`view-only-no-download` + `network-isolation`)와 Vitest 169/169, ESLint, Production Build 전부 무회귀로 확인했다. 사용자 수동 적용 후 저장소 docs/plan/SDV_MVP_DEFERRED.md가 살아있는 원본이다. 이번 outputs 파일은 적용 대기 개정본이며 원본을 자동 갱신하지 않았다. 기존 검증 이력을 보존하고 새 제품 계약과 구분한다.

## 실행 규칙

- 현재 작업에 꼭 필요한 기능과 실제로 실패하는 권한/비밀/데이터 무결성 문제를 우선 처리한다. 기능의 직접 테스트가 통과하면 해당 범위를 마친다.
- 단순 코드 취향, 추상화, 모든 가능한 예외의 선제 대응, 전 문서 재정렬은 완료를 막지 않는다.
- 이미 승인된 범위의 작은 구현 선택은 담당 에이전트가 결정하고 이유만 기록한다. 같은 설계를 반복 승인받지 않는다.
- 보완 항목의 선행 조건이 충족됐고 작은 변경으로 끝낼 수 있으면, Codex가 작업 시작 시 항목 ID·효과·수정 범위·검증·추가 비용을 한 번 제시해 사용자에게 이번에 포함할지 묻는다. 사용자가 수락하기 전에는 보완 항목을 자동으로 끼워 넣지 않는다. 기존 승인 범위의 필수 수정에는 적용하지 않는다.
- 실행자는 보완 후보를 발견하면 목록과 handoff에 남기고 승인된 작업을 계속한다. 동일한 후보를 상황 변화 없이 매번 다시 묻지 않는다.
- 직접 영향 테스트 우선. 공통 인증/스키마/토큰 경계 변경이면 Backend 회귀를 마무리 시 한 번 실행한다. 문서만 바뀐 작업은 빌드하지 않는다. 통과 후 새 변경·실패·구체적 우려가 없으면 반복하지 않는다.
- 상태를 `NOW`, `NEXT`, `BEFORE_MVP`, `BEFORE_DEPLOYMENT`, `LATER`, `CLOSED`로 구분한다. 미검증은 PASS로 계산하지 않는다.
- 단계별 합격은 범위 한정이다. UI나 Mock 테스트가 끝나도 전체 RAG/실제 Drive 완료라고 표시하지 않는다.
- 한 번에 실행 프롬프트 하나. Git 변경은 사용자만 수행하고 실행 전에 필요한 브랜치 작업을 안내한다. 매 작업 종료에 latest.md를 누적 갱신하고 다시 연다.

- **확인 불가(Unknown) 후보를 만나면 그 즉시 Scan을 멈춘다**: 이 후보가 실제로는 보였을 수도 있으므로, 그 뒤에 매기는 모든 위치 번호가 실제보다 하나씩 밀려있을 수 있다 - 계속 세면서 "아마 안 보였을 것"이라고 추측하지 않는다(Fail Closed). 확정적으로 배제된 후보(정책 거부, `isDefinitiveExclusion()`)는 위치를 건드리지 않고 계속 진행한다.
- **Bounded Candidate Scan 상한(`RagDiscoveryProperties.maxCandidateScan`, 이전 이름 `maxLookaheadCandidates`)을 정확히 지킨다**: 이전 구현은 `scanned<cap` 확인 후 Batch 전체(`query.size()`개)를 평가해, `cap=50,size=30`이면 실제로 60개까지 평가될 수 있는 결함이 있었다. 이제 Batch를 Fetch한 뒤 남은 평가 여력만큼만(`subList`) 자르고, 그 여력을 다 쓰면(Batch가 Trim됐으면) 원시 Catalog가 끝났는지(`Slice.hasNext()`)와 무관하게 상한 도달로 취급한다("더 읽어왔다"와 "다 평가했다"를 혼동하지 않음).
- **Deadline은 "새 작업을 시작하기 전"에만 확인하고, 이미 끝난 호출을 소급 무효화하지 않는다**: 이전 라운드에서는 Live 호출 직후에도 즉시 예산을 확인해 마지막/유일 호출이 예산을 넘기면 무조건 `partial=true`로 처리했다 - 이번 지시가 명확히 함: 예산은 "새 작업 시작"의 상한일 뿐 진행 중인 호출을 강제 취소하는 Timeout이 아니므로, 그 호출 이후 실제로 더 할 일이 없었다면(요청한 Page를 이미 다 채웠거나 원시 Catalog가 거기서 끝났다면) 응답은 완전한 것으로 취급한다. 반대로 더 확인해야 할 후보가 남아있었다면, 다음 후보/Batch를 시작하기 전의 확인이 정확히 그 지점에서 멈춘다.

### M10B 후속 교정 세션 스냅샷 - 연결 인가 세대(Connection Epoch) 손실 방지(2026-09-15, Claude Code, Backend Only)

**이 절은 위 두 M10B 절(원래 구현 완료 보고, 3개 결함군 보안 교정)을 대체하지 않는다** - 그 두 절이 이미 기록한 사실은 그대로 보존한다. 이 절은 그중 그룹 C(OAuth 재연결/공유 재확인 Fencing)를 위해 도입한 `connection_epoch`(V011) 자체의 증가 로직에서 별도로 발견된, 더 좁은 확정 결함 하나("make connection-epoch invalidation safe under concurrent disconnect requests")만 다룬다.

**확정 결함**: `SourceConnectionService.disconnect()`는 이 Method 맨 위에서 Unlocked 조회로 `SourceConnectionEntity`를 읽은 뒤, `sourceTokenStore.get().delete(id)`(`GoogleTokenService.revoke`)가 그 행을 `SELECT ... FOR UPDATE`로 잠갔다 - 그런데 그 Native Query는 Projection만 돌려줄 뿐 이미 Managed 상태인 `entity`의 Java 필드를 Refresh하지 않는다. 그 뒤 `entity.bumpConnectionEpoch()`가 이 Stale한 Java 값에 그대로 +1만 계산했다 - 두 Disconnect가 정확히 겹치면(둘 다 Row Lock을 얻기 전에 같은 낡은 값을 읽음) 두 번째 Commit이 첫 번째가 이미 반영한 증가를 같은 값으로 덮어써, 한쪽 증가가 통째로 유실됐다(최종 값이 +1만큼만 전진 - +2가 아니다). 이 상태에서는 두 번째 Disconnect보다 먼저 시작됐지만 첫 번째 Disconnect 이후에 시작된 OAuth 재인증 시도가, 그 유실 때문에 여전히 "지금 값과 일치"로 보여 두 번째 Disconnect의 무효화를 우회할 수 있었다.

**교정**: `entity.bumpConnectionEpoch()`(Java 쪽 +1 가정) 대신, `SourceConnectionJpaRepository`에 추가한 `incrementConnectionEpoch(id)`(Native `UPDATE source_connections SET connection_epoch = connection_epoch + 1 WHERE id = :id`)로 DB Column 자신을 기준으로 원자적으로 증가시킨다 - Java 쪽에 어떤 값이 캐시돼 있는지와 무관하게 항상 "지금 실제 저장된 값 + 1"이 된다. 일반 `UPDATE` 문 자체가 그 행에 대한 배타적 Write를 요구하므로, 겹치는 두 번째 호출은 첫 번째 호출의 Transaction이 Commit할 때까지 자연히 기다렸다가 그 Commit된 값 위에서 다시 +1 한다 - 별도의 명시적 Lock 획득 문이 필요 없다(`disconnect()`가 이미 같은 Transaction 안에서 `GoogleTokenService.revoke`를 통해 이 행을 Row Lock으로 잡아 두므로). 그 뒤 `findCurrentConnectionEpoch(id)`(1차 캐시를 우회하는 Native SELECT)로 그 결과를 다시 읽어 `entity.syncConnectionEpoch(...)`로 Managed Entity에 동기화한다.

**구현 중 실제로 재현한 2차 결함(자기 검증 과정에서 발견, 최종본에는 없음)**: 위 교정을 처음 `entity.updateTokenRef(null)`/`entity.changeStatus(DISABLED)` 호출 **뒤**에 넣었더니, 새로 추가한 Concurrency Test가 여전히 실패했다(기대 3, 실제 2) - 원인은 Hibernate의 Flush-Before-Query 기본 동작이었다: `entity`가 이미 Dirty해진 상태에서 같은 `source_connections` 테이블을 건드리는 Native Query(`incrementConnectionEpoch`)를 실행하면, Hibernate가 그 Query 실행 **직전**에 대기 중인 변경을 먼저 Auto-Flush한다 - 그 Auto-Flush가 Stale한 Java `connection_epoch` 값을 먼저 써 버려, 이미 다른 Transaction이 Commit해 둔 증가분을 그 자리에서 덮어썼다. 원자적 증가 호출을 `updateTokenRef`/`changeStatus`보다 **먼저**(entity가 아직 전혀 Dirty하지 않은 시점에) 옮겨 이 Auto-Flush 자체가 발생하지 않게 교정한 뒤에야 Test가 통과했다. 이 경위를 그대로 기록한다.

## 공부용 메모

Token은 Google API용 출입증이고 Master Key는 저장된 출입증을 잠그고 여는 열쇠다. DB에는 잠긴 출입증만 두고 열쇠는 실행 환경에서 별도로 제공한다. Frontend에는 Google Token을 전달하지 않고 연결 성공 여부만 보여준다.

**M10B 보안 교정(2026-09-15) - 세 가지 "낡은 정보를 새것으로 착각하는" 결함과 그 고치는 방법**

1. **그룹 A - 낙관적 잠금(Optimistic Lock)으로 "덮어쓰기 경쟁"을 막는다.**
   - 흐름: 게시자(User)가 공유 설정 화면을 열어 두면 그 순간의 `generation`(세대 번호)을 함께 받는다. 화면에서 저장을 누르면 그 세대 번호를 같이 서버로 보낸다. 그사이 관리자(Admin)가 먼저 차단을 저장해 세대가 올라가 있으면, 게시자의 저장 요청은 "누군가 먼저 바꿨다"는 뜻으로 거부된다.
   - 기법: JPA `@Version` - 이 Annotation을 필드 하나에 붙이면, Hibernate가 저장(UPDATE)할 때마다 자동으로 `WHERE ... AND generation = 그때_읽은_값`을 붙이고, 성공하면 값을 1 올린다. 두 사람이 동시에 같은 값을 읽고 저장하려 하면, 먼저 성공한 쪽만 반영되고 나중 사람은 예외(`ObjectOptimisticLockingFailureException`)를 받는다 - Java 코드로 "혹시 바뀌었나?"를 미리 물어보는 것보다 훨씬 안전하다(그 확인과 저장 사이에도 남이 끼어들 수 있기 때문).
   - 작은 예시: `@Version private long generation;`만 붙이면 끝난다. 개발자가 직접 `generation++`을 하면 안 된다(Hibernate가 대신 한다) - 실제로 이번에 `applyOwnerUpdate`/`applyAdminBlock`에서 수동 증가 코드를 지웠다(`DocumentShareEntity.java`).
   - 한계/테스트: `SelectiveSharingE2ETest.aStaleOwnerPatchCannotRemoveAnAdminBlockCommittedAfterItReadTheOldGeneration` - 다만 이 낙관적 잠금은 "먼저 커밋한 쪽이 이긴다"만 보장할 뿐, 사용자에게 "다시 불러오세요"라고 알려주는 것은 여전히 화면(Frontend)의 몫이다(이번 작업은 Backend만 다뤘다).

2. **그룹 B - "무엇을 잠글지"보다 "무엇을 기준으로 잠글지"가 더 중요하다.**
   - 흐름: 관리자가 위험한 파일 하나를 차단한다. 게시자가 그 공유를 지우고(Unshare) 같은 파일을 다시 게시(Republish)하면, 새 공유는 완전히 새로운 ID를 받는다 - "차단"이 옛 ID에만 붙어 있었다면 새 ID는 깨끗해 보여서 차단이 풀린 것처럼 동작했다.
   - 기법: 공유 ID가 아니라 "파일 자체의 신원"(Source ID + Document ID, 두 값의 조합)에 차단 표시를 따로 저장한다 - 사람으로 치면 "직원증 번호"가 아니라 "주민등록번호"에 블랙리스트를 거는 것과 같다. 직원증(공유 ID)은 재발급받아도, 주민등록번호(파일 신원)에 걸린 표시는 그대로 남는다.
   - 작은 예시: 새 테이블 `document_share_restrictions(source_id, document_id, blocked, ...)` - 공유를 새로 만들 때(`createShare`) 이 테이블을 먼저 확인해서, 이미 차단된 파일이면 새 공유도 처음부터 차단된 채로 만든다.
   - 한계/테스트: `SelectiveSharingE2ETest.adminBlockSurvivesOwnerUnshareAndRepublishOfTheSameFile` - 다만 관리자 해제 API가 여전히 "공유 ID"로 대상을 찾기 때문에, 아주 좁은 시간창에서 unshare와 관리자 차단이 정확히 겹치면 그 차단 시도 자체가 `NotFoundException`으로 명시적으로 실패한다(위 "잔여 창" 기록 참고) - 시스템이 스스로 복구하는 것이 아니라, ADMIN이 그 실패를 보고 새로고침 후 재게시된 새 공유를 다시 조회해 명시적으로 재시도해야 한다. 사소한 잔여 창이라 이번에는 새 Admin API 없이 그대로 기록만 남겼다.

3. **그룹 C - "지금 상태가 ACTIVE다"만으로는 부족하고, "언제부터 ACTIVE였는지"까지 봐야 한다.**
   - 흐름: 사용자가 Google 계정 연결 해제(Disconnect) 버튼을 누르는 순간, 그 이전에 이미 시작해 둔 재인증(OAuth) 시도나 공유 파일 확인 요청이 뒤늦게 도착할 수 있다. 상태만 보면 "지금 ACTIVE"로 보일 수 있어(재연결까지 끝났다면) 그 뒤늦은 요청을 새 요청처럼 착각하기 쉽다.
   - 기법: "연결 인가 세대"(Connection Epoch)라는 숫자를 하나 더 둔다 - 이 숫자는 오직 연결 해제(Disconnect)할 때만 올라간다(평소 Token 자동 갱신으로는 절대 안 올라간다). 재인증을 시작하는 순간 이 숫자를 적어 두고, 실제로 저장/활성화하기 직전에 지금 저장된 숫자와 다시 비교한다 - 다르면 "그사이 뭔가 있었다"는 뜻이므로 거부한다. 마치 회의실 예약표에 "몇 번째로 바뀐 예약인지" 도장을 찍어 두고, 나중에 도착한 사람이 옛 도장을 들고 오면 돌려보내는 것과 같다.
   - 작은 예시: `source_connections.connection_epoch`(V011) - `disconnect()`가 `bumpConnectionEpoch()`를 호출하고, `GoogleDriveOAuthService.commitCredential()`과 `EffectivePermissionService.decideShared()`가 각각 저장해 둔 값과 지금 값을 비교한다.
   - 한계/테스트: `SourceTokenConcurrencyTest`(재사용) + `GoogleDriveOAuthServiceTest.handleCallbackFailsClosedWhenTheConnectionEpochAdvancedAfterAuthorizationStarted` + `FileMetadataDiscoveryServiceTest.aDisconnectReconnectCycleDuringTheLiveCheckExcludesTheItemEvenThoughStatusReadsActiveAgain` - 다만 이 Epoch는 "연결 해제/재연결"만 감지하며, Google 쪽 파일 권한 자체가 바뀌는 것은 별도의 Live 재확인(`verifyCurrentMetadata`)이 담당한다(둘은 서로 다른 방어선이다). 또한 이번에 "신원이 한 번도 확인되지 않은(Legacy) 연결은 공유를 열어주지 않는다"는 검사(`SOURCE_IDENTITY_UNVERIFIED`)도 같은 자리에 추가했다 - `FileMetadataDiscoveryServiceTest.anUnverifiedLegacyProviderIdentityCannotGrantSharedDiscoveryUntilVerifiedBindingIsEstablished`.

**M10B 후속 교정(2026-09-15) - "잠긴 문이 있다"와 "그 문 뒤 값을 다시 읽었다"는 다른 이야기다**

- 흐름: 위 그룹 C가 도입한 `connection_epoch`를 두 번 연속 Disconnect(예: 사용자가 버튼을 두 번 누르거나, 탭을 두 개 열어 둔 경우)가 겹쳐서 건드리면 무슨 일이 생기는지가 이번 교정의 주제다. `disconnect()`는 이 값을 올리기 전에 이미 한 번 그 Source 행을 읽어 뒀는데(Method 맨 위), 그 뒤 실제로 행을 잠그는 절차(Token 삭제 경로)는 "잠갔다"는 사실만 확인해줄 뿐 "잠근 순간의 진짜 값"을 그 먼저 읽어 둔 Java 객체에 다시 넣어주지 않는다. 그래서 두 Disconnect가 겹치면 둘 다 "잠그기 전에 읽어 둔 낡은 값"에 각자 +1만 계산해, 실제로는 2번 올라야 할 값이 1번만 올라간 것처럼 보였다.
- 기법: "Java 객체의 값에 +1"이 아니라, DB에게 "너의 지금 값에 +1을 해줘"라고 그대로 위임한다(`UPDATE ... SET connection_epoch = connection_epoch + 1`) - 이러면 Java 쪽이 무엇을 기억하고 있는지와 전혀 무관하게, 항상 그 순간 DB에 실제로 적힌 값을 기준으로 계산된다. 마치 "내가 마지막으로 본 은행 잔액에 만원을 더해서 새로 적어라"가 아니라 "지금 통장에 있는 잔액에 만원을 더해라"라고 은행에 직접 시키는 것과 같다 - 내가 마지막으로 본 잔액이 이미 낡았어도 상관없다.
- 작은 예시: `SourceConnectionJpaRepository.incrementConnectionEpoch(id)`(원자적 증가) + `findCurrentConnectionEpoch(id)`(그 결과를 다시 읽음) + `SourceConnectionEntity.syncConnectionEpoch(그 값)`(Java 객체에 동기화) - `SourceConnectionService.disconnect()`가 이 세 단계를 **Token 삭제 직후, 다른 어떤 필드도 아직 건드리기 전에** 수행한다. 개발 중 이 순서를 반대로 했더니(Status/TokenRef를 먼저 바꾼 뒤 이 세 단계를 나중에 실행) Hibernate가 "다른 변경사항을 마저 반영해야겠다"며 그 원자적 증가보다 먼저 낡은 값을 저장해 버려 똑같은 결함이 재현됐다 - 순서 자체가 교정의 핵심이었다.
- 한계/테스트: `SourceTokenConcurrencyTest.twoOverlappingDisconnectsBothAdvanceTheConnectionEpochWithoutLosingEitherIncrement`(실제 2-Thread로 겹치는 Disconnect를 재현, `CountDownLatch`로 정확한 시점에 멈춰 세운다 - Sleep 없음) - 이 교정은 `connection_epoch` 하나에만 적용되고, 실제 Google 계정으로 정확히 이 순간에 두 번 Disconnect를 누르는 것은 검증하지 않았다(Mock/Testcontainers 기반 재현이다).

**M16C(2026-09-16) - "documentId"와 "shareId"는 이름이 비슷해도 완전히 다른 것이다**

- 흐름: B(수신자)가 문서 검색 화면에서 "SDV 다운로드"를 누르면, 그 요청은 `documentId`가 아니라 `shareId`(그 파일을 지금 보여준 바로 그 공유의 ID)로 나가야 한다. 같은 문서라도 옛날에 철회된 공유와 지금 살아있는 공유는 ID가 다르므로, `documentId`로 추측해서 부르면 이미 죽은 공유를 부르거나(실패) 반대로 위험할 수 있다.
- 기법: Backend가 검색 결과(`RagFileItem`) 안에 "지금 이 항목을 실제로 통과시킨 공유의 ID"(`shareId`)를 함께 실어 보낸다 - Client는 이 값을 그대로 다운로드 Endpoint에 전달할 뿐, 스스로 계산/추측하지 않는다. 그리고 Client가 이 값을 위조하거나 낡은 값을 보내도, 다운로드 Endpoint(`SharedFileDownloadService`, M10C에서 이미 구현됨)가 매번 서버에서 다시 전체 인가를 재확인하므로 이 값은 어디까지나 "UI가 버튼을 보여줄지 말지 정하는 힌트"일 뿐 인가 자체가 아니다("UI action information is only a hint; the download endpoint remains authoritative").
- 작은 예시: `RagFileItem(documentId=100, shareId=57, allowedActions=["VIEW","DOWNLOAD"])` - Frontend는 `documentId`로 화면에 목록을 그리고, 다운로드 버튼을 누르면 `GET /api/shares/57/download`(정확히 `shareId`)를 부른다. `FileMetadataDiscoveryService.toItem(document, live, share)`가 이 결합을 만든다 - `document.getId()`(documentId)와 `share.getId()`(shareId)를 절대 같은 변수에 담지 않는다.
- 한계/테스트: `FileMetadataDiscoveryServiceTest.shareIdAndAllowedActionsAreBoundToTheExactSurvivingShareNotAnotherOne`(서로 다른 두 공유의 shareId/allowedActions가 정확히 자신의 파일에만 붙는지 교차 확인) - 다만 이 값 자체는 "힌트"이므로, 실제 다운로드 성공/실패는 여전히 M10C의 실제 재인가 로직에 달려 있다(이번 Slice가 그 로직을 검증한 것은 아니다).

**M11 후속 교정(2026-09-16, 같은 날 이어진 Claude Code 세션) - "한 번 색인됐다"와 "지금 이 색인이 유효하다"는 다른 이야기다**

1. **그룹 1 - 파일이 바뀌었으면 다시 읽어야 한다.**
   - 흐름: 게시자가 공유를 만든 뒤 원본 파일 내용을 실제로 수정하면(Google Docs에 새 문단을 쓰는 것처럼), 그 변경은 `SOURCE_DOCUMENT_CHANGED`라는 Catalog Sync 이벤트로만 알려졌다 - 색인 Consumer는 이 이벤트 타입을 아예 쳐다보지 않았다. 그래서 최초 공유 시점의 옛 내용으로만 계속 답하게 될 수 있었다.
   - 기법: 이 Consumer가 이제 `INDEX_REQUESTED`뿐 아니라 `SOURCE_DOCUMENT_CHANGED`도 같은 `IndexOrchestrator`로 넘긴다 - `IndexOrchestrator` 자신이 매번 "지금 공유가 살아있는가"부터 새로 확인하므로, 비공개(한 번도 공유된 적 없는) 문서의 평범한 내용 변경은 여전히 Google Fetch 자체를 절대 유발하지 않는다.
   - 작은 예시: `IndexRequestedConsumer.isTriggeringEventType(eventType)`가 두 이벤트 타입 모두 `true`를 반환한다 - 나머지(삭제/권한 변경)는 그대로 무시.
   - 재연결도 비슷한 구멍이었다: Disconnect가 이 Source의 Embedding을 전부 지우는데, 재연결 자체는 아무 새 색인 작업도 예약하지 않아서 사람이 수동으로 뭔가를 다시 건드리기 전까지는 색인이 영원히 비어 있었다. 이제 `GoogleDriveOAuthService`가 검증된 같은 계정 재연결 성공 직후, 그 Source의 지금 활성+비차단 공유 문서만(상한 200개) 새 색인 요청을 예약한다.
   - Backfill(운영자가 Pipeline을 켤 때 밀린 것을 메꾸는 도구)도 "과거에 딱 한 번 INDEXED로 기록된 적 있는가"만 보고 있었다 - unshare가 그 Embedding을 지운 뒤 다시 공유해도 "이미 끝난 문서"로 착각해 영원히 후보에서 빠졌다. 이제는 "지금 이 문서의 현재 Version에 대응하는 Embedding이 실제로 존재하는가"를 직접 확인한다.
   - 한계/테스트: `IndexBackfillServiceTest`(5, 실제 PostgreSQL), `SourceDocumentJpaRepositoryTest`의 재연결 스케줄링 조회 3개, `IndexOrchestratorReconnectRaceConcurrencyTest` - 다만 재연결 예약은 한 번에 최대 200개만 처리한다(Bounded) - 그보다 많은 밀린 문서는 운영자가 여전히 Backfill을 수동으로 이어 호출해야 한다(설계상 그대로).

2. **그룹 2 - "지금 ACTIVE다"만으로는 부족하고, "그 ACTIVE가 내가 알던 바로 그 세대인가"까지 봐야 한다(M10B 그룹 C와 같은 종류의 결함, 이번엔 색인 발행 지점).**
   - 흐름: 색인 작업이 Google 파일을 읽고 AI로 Embedding을 만드는 동안(수 초~수십 초 걸릴 수 있다), 그 사이 누군가 연결을 끊었다 같은 계정으로 다시 연결하거나, 공유를 취소하고 새로 게시하거나, 관리자가 차단했다 해제할 수 있다. 발행 직전 재검증이 "지금 연결 상태가 ACTIVE인가"/"지금 공유가 하나라도 활성인가"만 봤다면, 이 세 경우 모두 "그렇다"로 보여서 옛(더 이상 유효하지 않은 전제로 시작된) 작업이 그대로 통과해 버릴 수 있었다.
   - 기법: 색인 작업을 시작하는 바로 그 순간의 "세대 번호" 두 개를 함께 적어 둔다 - 연결의 `connectionEpoch`(M10B가 이미 만들어 둔, Disconnect할 때만 올라가는 숫자)와 공유 자신의 `generation`(JPA `@Version`, 등급/행위가 바뀌거나 차단/해제될 때마다 자동으로 올라가는 숫자). 발행 직전에 이 두 숫자를 지금 DB에 실제로 잠긴 값과 정확히 비교해서, 하나라도 다르면 "그 사이 뭔가 있었다"는 뜻으로 발행을 포기한다 - 마치 회의실 예약표에 도장을 찍어 두고 나중에 옛 도장을 들고 온 사람을 돌려보내는 것과 같다(M10B 그룹 C 설명 참고).
   - "확인"과 "보호"는 다르다는 것도 이번에 새로 알게 된 부분이다: 공유 행을 그냥 읽기만 하면, 읽은 직후 다른 요청이 그 행을 바꿔서 커밋해도 이 색인 작업은 알 방법이 없다. 그래서 공유 행도 `SELECT ... FOR UPDATE`로 잠근다(연결→문서→공유 순서, 항상 이 순서로만 잠가 Deadlock을 만들지 않는다) - 이러면 그 순간 공유를 바꾸려는 다른 요청(`updateShare`/`adminSetBlocked`)이 이 색인 작업의 Transaction이 끝날 때까지 자연히 기다린다.
   - AI 파싱이 끝난 직후에도 한 번 더 확인한다(DB Lock을 아직 열기 전에) - Google 쪽에서 그 사이 접근 권한이나 Version이 바뀌었는지를 실제로 다시 물어본다(`verifyCurrentMetadata`, Content Byte는 다시 받지 않는다). Catalog Sync가 아직 그 변화를 못 따라잡은 짧은 틈을 메운다.
   - SKIPPED/FAILED 같은 "실패" 기록도 똑같이 보호한다 - 낡은 시도가 뒤늦게 "실패했다"고 기록하려 할 때, 이미 더 새로운 시도가 성공적으로 색인을 마쳤다면 그 성공을 절대 덮어쓰지 않는다.
   - 작은 예시: `IndexOrchestrator.publishGeneration`의 새 확인 3종(`connectionEpoch` 비교, `documentShareJpaRepository.findByIdForUpdate`로 잠근 뒤 `shareId`+`generation` 비교), `SourceDocumentJpaRepository.updateIndexStatusIfCurrent`/`updateIndexStatusIfNotIndexed`(조건부 갱신, 이미 `INDEXED`면 절대 덮어쓰지 않는다).
   - 한계/테스트: `IndexOrchestratorTest`의 신규 4개(Epoch 변경/공유 변경/Post-parse Recheck 실패/버전 변경), `IndexOrchestratorReconnectRaceConcurrencyTest`(재연결 경합), `IndexOrchestratorShareRaceConcurrencyTest`(unshare+재게시, 차단+해제 경합) - 전부 Revert-Rerun-Restore로 "이 확인을 빼면 실제로 실패한다"를 먼저 확인한 뒤 원복해 통과를 재확인했다(추측이 아니다). 이 Epoch/Generation Fencing은 여전히 "두 Transaction이 완전히 동시에 Commit을 다투는" 초-미세 Interleaving까지 재현한 것은 아니다(Postgres 행 Lock이 구조적으로 막는 범주) - 이 Test들은 "먼저 시작한 작업이 나중에 재개될 때 반드시 최신 상태를 다시 읽는다"를 검증한다.

3. **그룹 3 - "안전한 사유 문자열"이라고 부른 것이 사실은 임의 텍스트였다.**
   - 흐름: AI 서비스가 실패 사유로 보낸 텍스트(`IndexOutcome.reason()`)를 `safeReason()`이라는 이름의 메서드가 그대로 통과시켜 DB `index_reason`과 예외 메시지에 실었다 - 이름과 달리 "안전"이 아니라 "원본 그대로"였다. 종결 실패(재시도 소진) 처리도 표준 `DeadLetterPublishingRecoverer`를 그대로 썼는데, 이건 원본 Kafka Record의 Key/Value 전체와 예외 메시지/Stack Trace를 Header로 그대로 DLT에 옮긴다 - Payload에 누가 실수로(또는 악의적으로) 무엇을 더 넣었어도 그대로 새어 나간다.
   - 기법: "원본 텍스트를 다듬어서 옮긴다"가 아니라 "원본 텍스트를 아예 쳐다보지 않는다"로 바꿨다. 실패 사유는 AI 서비스가 뭐라고 했든 상관없이 그 실패의 **종류**(형식 미지원/텍스트 없음/처리 실패)에 대응하는 미리 정해진 고정 문자열 중 하나로만 기록한다. DLT도 원본 Record를 감싸는 대신, 완전히 새로 조립한 최소 봉투(고정 사유 코드 + 안전한 Broker 좌표(Topic/Partition/Offset) + Best-effort eventId/documentId)만 보낸다 - 이 봉투를 만드는 코드 자체가 원본 값을 읽는 줄이 없으므로, Payload에 무엇이 섞여 있었든 새어 나갈 방법이 없다.
   - 작은 예시: `IndexOrchestrator.reasonCodeFor(ParseOutcomeKind)`(고정 코드 매핑), `IndexConsumerErrorHandlingConfig.buildSanitizedDeadLetterEnvelope`(원본 Record를 감싸지 않고 새로 조립).
   - 한계/테스트: `IndexConsumerErrorHandlingConfigTest`(8, 순수 Mockito) - 원본 Payload에 가짜 비밀(Canary) 필드를 심어 두고, 그 값이 DLT 봉투 어디에도 나타나지 않음을 직접 확인한다. DB 기록 자체가 실패하면(Down 등) 이 메서드가 예외를 삼키지 않고 그대로 전파해 Consumer가 그 Record를 "회복됨"으로 착각하지 않게 한다는 것도 별도로 확인했다.

**M11 후속 교정 2차(2026-09-16, 같은 날 이어진 별도 교정 세션) - "Transaction 경계 없이 조건부 UPDATE를 하나 더 썼다"는 여전히 미완성이었다**

바로 위 절이 서술한 1차 교정(같은 날) 자체에 세 가지 실행 경계/내구성 결함이 남아 있었다 - 사용자가 직접 지적해 이 세션에서 표적 교정했다. 재설계가 아니라 정확히 이 세 가지만 고쳤다.

1. **비성공 기록(SKIPPED_UNSUPPORTED/SKIPPED_NO_TEXT)에 Transaction이 없었다.** `IndexOrchestrator.process()`/`handleUnverifiedContent()`가 `updateIndexStatusIfCurrent`(`@Modifying` Custom Query)를 감싸는 Transaction 없이 직접 호출했다 - **실제로 재현했다**: Test에서 이 Method를 Transaction 밖에서 그대로 호출하면 `jakarta.persistence.TransactionRequiredException`이 즉시 발생한다(Spring Data JPA는 상속받은 기본 CRUD Method(`save`/`existsById` 등)만 자동으로 Transaction을 열어주고, Repository Interface에 직접 선언한 Custom `@Modifying` Query는 그렇지 않다 - 이번에 직접 확인 전까지는 추정이었다). 이제 성공(`publishGeneration`)과 완전히 같은 짧은 새 Transaction/Lock 순서(`source_connections`→`source_documents`→`document_shares`)를 공유하는 `finalizeNonSuccess`/`lockAndRevalidate`로 통합했다 - 비성공 기록도 연결 Epoch/공유 Generation 펜싱을 성공 발행과 동일하게 받는다("indexStatus != INDEXED"만으로는 세대 펜싱이 아니라는 지적을 그대로 반영). Revert-Rerun-Restore로 직접 확인(`IndexOrchestratorNonSuccessFencingConcurrencyTest`, 5개, Test 자신은 `@Transactional`을 쓰지 않고 실제 Proxied Orchestrator를 호출).
2. **DLT 확인 없이 "복구됨"으로 넘어갈 수 있었다.** `recordTerminalFailure`가 `eventId`를 못 구하면 DB 기록 자체를 건너뛰었고, 그 뒤 DLT 발행 실패도 항상 삼켰다 - 두 안전장치가 동시에 없어도 Consumer는 이 Record를 "회복됨"으로 처리해 자동 Ack할 수 있었다. `kafkaTemplate.send()`의 반환 Future도 결과를 기다리지 않아 "호출이 반환됨"과 "실제 전달 확인"을 혼동했다. 이제 `tryRecordDurableDisposition`이 `eventId`가 없어도 안전한 Broker 좌표(Topic/Partition/Offset)에서 결정론적 합성 Key를 만들어 항상 DB 기록을 시도하고, 그 DB 기록 자체가 실패할 때만 `confirmSanitizedDeadLetterDelivery`(Bounded Timeout으로 실제 `Future.get()` 확인, 실패/Timeout/예외적 완료 전부 예외로 재전파)로 넘어간다 - DB 성공 시에만 DLT가 Best-effort로 남는다. 이 교정과 함께, 신뢰 가능한 스냅샷이 없는 이 지점은 더 이상 `source_documents.index_status`를 전혀 건드리지 않는다("record the event failure without blindly changing document state"). `IndexConsumerErrorHandlingConfigTest`를 실제 `buildRecoverer`(구성된 복구 경로 그 자체) 직접 호출 기준으로 재작성(9개) - Helper 단위 검증만으로는 이 분기 자체를 검증하지 못했었다.
3. **완료 원장 기록이 "존재 확인 후 저장"이었다.** `IndexRequestedConsumer.recordProcessed`/종결 실패 기록 둘 다 할당된 복합 ID에 `JpaRepository.save()`를 썼다 - Write-Once를 보장하지 않는다. `ProcessedEventJpaRepository.insertIfAbsent`(신규, Native `INSERT ... ON CONFLICT (event_id, consumer_name) DO NOTHING`, 새 Migration 없이 기존 V012 제약만 사용)로 교체해 First-Writer-Wins를 원자적으로 보장한다 - 낡은 종결 실패가 이미 기록된 성공을 절대 덮어쓰지 못한다. 이 교체 과정에서 `IndexRequestedConsumer.onMessage()` 자신도 같은 "Custom Query는 자동 Transaction이 없다" 문제에 새로 부딪혀(이 원장 기록 자체가 `.save()`에서 `insertIfAbsent`로 바뀌며 처음 노출된 문제), `onMessage()` 전체를 `@Transactional`로 감싸는 대신(그러면 `process()` 안의 Google/Python 외부 호출까지 Ambient Transaction 아래 들어가 버린다) 원장 기록 한 줄만 감싸는 전용 `TransactionTemplate`을 추가했다. `ProcessedEventJpaRepositoryTest`(동시 삽입 경합 2개) + `IndexRequestedConsumerLedgerGapTest`(발행 성공~원장 기록 사이 Crash 후 재전달 2개, "Safe fresh reprocessing"과 "철회된 작업 복구 불가"를 각각 직접 확인).

문서 정정: `docs/runbooks/M11_INDEXING_ACTIVATION.md`의 Backfill 중복 방지 절이 "check-then-insert 가드가 동시 중복 적재를 막는다"고 과장했던 것을 "순차 호출만 막고, 진짜 동시 호출은 안전망일 뿐 보장이 아니다"로 정정했고, "실용적 호출 경로" 절이 아직 만들지 않은 제안(Runner/REPL)을 이미 있는 것처럼 서술했던 것을 "제안일 뿐, 이 교정이 만들지 않았다"로 정정했으며, Backfill 종료 조건을 `publishedCount()==0`이 아니라 `lastShareId`가 전진하지 않음(진짜 Scan 종료)으로 정정했다(`IndexBackfillServiceTest` 신규 2개로 그 구분을 직접 검증).
