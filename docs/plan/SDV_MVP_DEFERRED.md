# SDV MVP 우선 구현 · 보완 목록

2026-09-13 사용자 지시로 도입. 목적은 동작하는 MVP와 프론트엔드를 빠르게 완성하면서 미완료 사항을 잊지 않는 것이다. 문서 작성은 해당 기능의 구현이나 테스트 완료를 의미하지 않는다.

## 문서 위치와 관리

사용자 수동 적용 후 저장소 docs/plan/SDV_MVP_DEFERRED.md가 살아있는 원본이다. 이번 outputs 파일은 적용 대기 개정본이며 원본을 자동 갱신하지 않았다. 기존 검증 이력을 보존하고 새 제품 계약과 구분한다.

Codex와 Claude는 매 작업 시작에 최신 보완 목록, 현재 Git 상태, latest.md를 먼저 읽는다. Claude는 여전히 `docs/workmd/**`에 접근하지 않는다.

## 실행 규칙

- 현재 작업에 꼭 필요한 기능과 실제로 실패하는 권한/비밀/데이터 무결성 문제를 우선 처리한다. 기능의 직접 테스트가 통과하면 해당 범위를 마친다.
- 단순 코드 취향, 추상화, 모든 가능한 예외의 선제 대응, 전 문서 재정렬은 완료를 막지 않는다.
- 이미 승인된 범위의 작은 구현 선택은 담당 에이전트가 결정하고 이유만 기록한다. 같은 설계를 반복 승인받지 않는다.
- 보완 항목의 선행 조건이 충족됐고 작은 변경으로 끝낼 수 있으면, Codex가 작업 시작 시 항목 ID·효과·수정 범위·검증·추가 비용을 한 번 제시해 사용자에게 이번에 포함할지 묻는다. 사용자가 수락하기 전에는 보완 항목을 자동으로 끼워 넣지 않는다. 기존 승인 범위의 필수 수정에는 적용하지 않는다.
- 실행자는 보완 후보를 발견하면 목록과 handoff에 남기고 승인된 작업을 계속한다. 동일한 후보를 상황 변화 없이 매번 다시 묻지 않는다.
- 직접 영향 테스트 우선. 공통 인증/스키마/토큰 경계 변경이면 Backend 회귀를 마무리 시 한 번 실행한다. 문서만 바뀐 작업은 빌드하지 않는다. 통과 후 새 변경·실패·구체적 우려가 없으면 반복하지 않는다.
- 상태를 `NOW`, `NEXT`, `BEFORE_MVP`, `BEFORE_DEPLOYMENT`, `LATER`, `CLOSED`로 구분한다. 미검증은 PASS로 계산하지 않는다.
- 단계별 합격은 범위 한정이다. UI나 Mock 테스트가 끝나도 전체 RAG/실제 Drive 완료라고 표시하지 않는다.
- 한 번에 실행 프롬프트 하나. Git 변경은 사용자만 수행하고 실행 전에 필요한 브랜치 작업을 안내한다. 매 작업 종료에 latest.md를 누적 갱신하고 다시 연다.

## 승인된 진행 순서 (v1.5, 2026-09-15)

**진행 상태 갱신(2026-09-15, 같은 날 M10B 세션)**: 1번(M16B 통합)은 사용자가 이미 수행했다(`develop` merge #35, HEAD `629364f`). 2번(M10B Backend)은 아래 MVP-32/33/05/37 근거대로 Backend Only 구현·Mock/Testcontainers 검증까지 완료했다 - 이 순서 목록 자체(1~7)는 계획으로서 그대로 보존하고, 실제 진행 상태는 각 MVP 항목 표에서 추적한다(이 목록을 지금 다시 쓰지 않는다).

**진행 상태 갱신(2026-09-15, 같은 날 M10B 보안 교정 세션)**: 같은 날 이어진 별도 세션이, 위 M10B 완료 보고의 500/500 회귀가 다루지 않았던 세 가지 동시성/펜싱 결함(공유 낙관적 잠금 미완성, 관리자 차단이 unshare→재게시로 우회 가능, OAuth 재연결/공유 재확인이 낡은 판단을 새 상태로 착각할 수 있음)을 발견·교정했다 - 상세는 아래 "M10B 보안 교정 세션 스냅샷" 참고. 이 순서 목록(1~7)과 MVP-28이 "MVP 완료 직후 최우선"이라는 승인된 우선순위는 변경되지 않는다.

1. 현재 M16B uncommitted 작업을 사용자가 검토·통합한다. 문서 복사 전에 진행 중인 다른 편집을 마친다.
2. M10B: 일반 USER 연결·파일 단위 명시 공유·게시자 위임·동일 계정 재연결 복구.
3. M10C: SDV 인가 다운로드. M16C: 내 Drive 선택기·수신자/등급/행위 확인·공유 UI.
4. M09 잔여 consumer/멱등성/retry/DLQ 및 활성화 gate와 M11 색인, M12 live retrieval을 연결한다.
5. M13/14 자연어 파일 찾기와 내용 질문·답변·인용, M15/16 필요한 감사/UI를 완성한다.
6. M17/18 일반 USER 실제 OIDC·A 게시/B 허용/C 거부·다운로드·철회/복구까지 통과한다.
7. MVP 직후 최우선은 MVP-28 CSS 고급화. 원본 저장(STO-001)은 이후 별도 설계/우선순위로 진행한다.

연결은 기본 비공개이다. 공통 검색/AI/다운로드에는 명시적 공유만 포함한다. 수신자 B의 SDV 인가와 게시자 A의 파일-bound Source 인가를 분리한다. B의 native Google 권한/DWD는 필요하지 않다. 관리자도 비공개 저장소나 콘텐츠에 자동 접근하지 않는다. 이전 기록의 owner-only 모델은 현재 목표로 사용하지 않는다.

- **확인 불가(Unknown) 후보를 만나면 그 즉시 Scan을 멈춘다**: 이 후보가 실제로는 보였을 수도 있으므로, 그 뒤에 매기는 모든 위치 번호가 실제보다 하나씩 밀려있을 수 있다 - 계속 세면서 "아마 안 보였을 것"이라고 추측하지 않는다(Fail Closed). 확정적으로 배제된 후보(정책 거부, `isDefinitiveExclusion()`)는 위치를 건드리지 않고 계속 진행한다.
- **Bounded Candidate Scan 상한(`RagDiscoveryProperties.maxCandidateScan`, 이전 이름 `maxLookaheadCandidates`)을 정확히 지킨다**: 이전 구현은 `scanned<cap` 확인 후 Batch 전체(`query.size()`개)를 평가해, `cap=50,size=30`이면 실제로 60개까지 평가될 수 있는 결함이 있었다. 이제 Batch를 Fetch한 뒤 남은 평가 여력만큼만(`subList`) 자르고, 그 여력을 다 쓰면(Batch가 Trim됐으면) 원시 Catalog가 끝났는지(`Slice.hasNext()`)와 무관하게 상한 도달로 취급한다("더 읽어왔다"와 "다 평가했다"를 혼동하지 않음).
- **Deadline은 "새 작업을 시작하기 전"에만 확인하고, 이미 끝난 호출을 소급 무효화하지 않는다**: 이전 라운드에서는 Live 호출 직후에도 즉시 예산을 확인해 마지막/유일 호출이 예산을 넘기면 무조건 `partial=true`로 처리했다 - 이번 지시가 명확히 함: 예산은 "새 작업 시작"의 상한일 뿐 진행 중인 호출을 강제 취소하는 Timeout이 아니므로, 그 호출 이후 실제로 더 할 일이 없었다면(요청한 Page를 이미 다 채웠거나 원시 Catalog가 거기서 끝났다면) 응답은 완전한 것으로 취급한다. 반대로 더 확인해야 할 후보가 남아있었다면, 다음 후보/Batch를 시작하기 전의 확인이 정확히 그 지점에서 멈춘다.

### M10B 후속 교정 세션 스냅샷 - 연결 인가 세대(Connection Epoch) 손실 방지(2026-09-15, Claude Code, Backend Only)

**이 절은 위 두 M10B 절(원래 구현 완료 보고, 3개 결함군 보안 교정)을 대체하지 않는다** - 그 두 절이 이미 기록한 사실은 그대로 보존한다. 이 절은 그중 그룹 C(OAuth 재연결/공유 재확인 Fencing)를 위해 도입한 `connection_epoch`(V011) 자체의 증가 로직에서 별도로 발견된, 더 좁은 확정 결함 하나("make connection-epoch invalidation safe under concurrent disconnect requests")만 다룬다.

**확정 결함**: `SourceConnectionService.disconnect()`는 이 Method 맨 위에서 Unlocked 조회로 `SourceConnectionEntity`를 읽은 뒤, `sourceTokenStore.get().delete(id)`(`GoogleTokenService.revoke`)가 그 행을 `SELECT ... FOR UPDATE`로 잠갔다 - 그런데 그 Native Query는 Projection만 돌려줄 뿐 이미 Managed 상태인 `entity`의 Java 필드를 Refresh하지 않는다. 그 뒤 `entity.bumpConnectionEpoch()`가 이 Stale한 Java 값에 그대로 +1만 계산했다 - 두 Disconnect가 정확히 겹치면(둘 다 Row Lock을 얻기 전에 같은 낡은 값을 읽음) 두 번째 Commit이 첫 번째가 이미 반영한 증가를 같은 값으로 덮어써, 한쪽 증가가 통째로 유실됐다(최종 값이 +1만큼만 전진 - +2가 아니다). 이 상태에서는 두 번째 Disconnect보다 먼저 시작됐지만 첫 번째 Disconnect 이후에 시작된 OAuth 재인증 시도가, 그 유실 때문에 여전히 "지금 값과 일치"로 보여 두 번째 Disconnect의 무효화를 우회할 수 있었다.

**교정**: `entity.bumpConnectionEpoch()`(Java 쪽 +1 가정) 대신, `SourceConnectionJpaRepository`에 추가한 `incrementConnectionEpoch(id)`(Native `UPDATE source_connections SET connection_epoch = connection_epoch + 1 WHERE id = :id`)로 DB Column 자신을 기준으로 원자적으로 증가시킨다 - Java 쪽에 어떤 값이 캐시돼 있는지와 무관하게 항상 "지금 실제 저장된 값 + 1"이 된다. 일반 `UPDATE` 문 자체가 그 행에 대한 배타적 Write를 요구하므로, 겹치는 두 번째 호출은 첫 번째 호출의 Transaction이 Commit할 때까지 자연히 기다렸다가 그 Commit된 값 위에서 다시 +1 한다 - 별도의 명시적 Lock 획득 문이 필요 없다(`disconnect()`가 이미 같은 Transaction 안에서 `GoogleTokenService.revoke`를 통해 이 행을 Row Lock으로 잡아 두므로). 그 뒤 `findCurrentConnectionEpoch(id)`(1차 캐시를 우회하는 Native SELECT)로 그 결과를 다시 읽어 `entity.syncConnectionEpoch(...)`로 Managed Entity에 동기화한다.

**구현 중 실제로 재현한 2차 결함(자기 검증 과정에서 발견, 최종본에는 없음)**: 위 교정을 처음 `entity.updateTokenRef(null)`/`entity.changeStatus(DISABLED)` 호출 **뒤**에 넣었더니, 새로 추가한 Concurrency Test가 여전히 실패했다(기대 3, 실제 2) - 원인은 Hibernate의 Flush-Before-Query 기본 동작이었다: `entity`가 이미 Dirty해진 상태에서 같은 `source_connections` 테이블을 건드리는 Native Query(`incrementConnectionEpoch`)를 실행하면, Hibernate가 그 Query 실행 **직전**에 대기 중인 변경을 먼저 Auto-Flush한다 - 그 Auto-Flush가 Stale한 Java `connection_epoch` 값을 먼저 써 버려, 이미 다른 Transaction이 Commit해 둔 증가분을 그 자리에서 덮어썼다. 원자적 증가 호출을 `updateTokenRef`/`changeStatus`보다 **먼저**(entity가 아직 전혀 Dirty하지 않은 시점에) 옮겨 이 Auto-Flush 자체가 발생하지 않게 교정한 뒤에야 Test가 통과했다. 이 경위를 그대로 기록한다.

## 공부용 메모

Token은 Google API용 출입증이고 Master Key는 저장된 출입증을 잠그고 여는 열쇠다. DB에는 잠긴 출입증만 두고 열쇠는 실행 환경에서 별도로 제공한다. Frontend에는 Google Token을 전달하지 않고 연결 성공 여부만 보여준다.

**M10B 보안 교정(2026-09-15) - 세 가지 "낡은 정보를 새것으로 착각하는" 결함과 그 고치는 방법**

1. **그룹 A - 낙관적 잠금(Optimistic Lock)으로 "덮어쓰기 경쟁"을 막는다.**
   - 흐름: 게시자(User)가 공유 설정 화면을 열어 두면 그 순간의 `generation`(세대 번호)을 함께 받는다. 화면에서 저장을 누르면 그 세대 번호를 같이 서버로 보낸다. 그사이 관리자(Admin)가 먼저 차단을 저장해 세대가 올라가 있으면, 게시자의 저장 요청은 "누군가 먼저 바꿨다"는 뜻으로 거부된다.
   - 기법: JPA `@Version` - 이 Annotation을 필드 하나에 붙이면, Hibernate가 저장(UPDATE)할 때마다 자동으로 `WHERE ... AND generation = 그때_읽은_값`을 붙이고, 성공하면 값을 1 올린다. 두 사람이 동시에 같은 값을 읽고 저장하려 하면, 먼저 성공한 쪽만 반영되고 나중 사람은 예외(`ObjectOptimisticLockingFailureException`)를 받는다 - Java 코드로 "혹시 바뀌었나?"를 미리 물어보는 것보다 훨씬 안전하다(그 확인과 저장 사이에도 남이 끼어들 수 있기 때문).
   - 작은 예시: `@Version private long generation;`만 붙이면 끝난다. 개발자가 직접 `generation++`을 하면 안 된다(Hibernate가 대신 한다) - 실제로 이번에 `applyOwnerUpdate`/`applyAdminBlock`에서 수동 증가 코드를 지웠다(`DocumentShareEntity.java`).
   - 한계/테스트: `SelectiveSharingE2ETest.aStaleOwnerPatchCannotRemoveAnAdminBlockCommittedAfterItReadTheOldGeneration` - 다만 이 낙관적 잠금은 "먼저 커밋한 쪽이 이긴다"만 보장할 뿐, 사용자에게 "다시 불러오세요"라고 알려주는 것은 여전히 화면(Frontend)의 몫이다(이번 작업은 Backend만 다뤘다).

2. **그룹 B - "무엇을 잠글지"보다 "무엇을 기준으로 잠글지"가 더 중요하다.**
   - 흐름: 관리자가 위험한 파일 하나를 차단한다. 게시자가 그 공유를 지우고(Unshare) 같은 파일을 다시 게시(Republish)하면, 새 공유는 완전히 새로운 ID를 받는다 - "차단"이 옛 ID에만 붙어 있었다면 새 ID는 깨끗해 보여서 차단이 풀린 것처럼 동작했다.
   - 기법: 공유 ID가 아니라 "파일 자체의 신원"(Source ID + Document ID, 두 값의 조합)에 차단 표시를 따로 저장한다 - 사람으로 치면 "직원증 번호"가 아니라 "주민등록번호"에 블랙리스트를 거는 것과 같다. 직원증(공유 ID)은 재발급받아도, 주민등록번호(파일 신원)에 걸린 표시는 그대로 남는다.
   - 작은 예시: 새 테이블 `document_share_restrictions(source_id, document_id, blocked, ...)` - 공유를 새로 만들 때(`createShare`) 이 테이블을 먼저 확인해서, 이미 차단된 파일이면 새 공유도 처음부터 차단된 채로 만든다.
   - 한계/테스트: `SelectiveSharingE2ETest.adminBlockSurvivesOwnerUnshareAndRepublishOfTheSameFile` - 다만 관리자 해제 API가 여전히 "공유 ID"로 대상을 찾기 때문에, 아주 좁은 시간창에서 unshare와 관리자 차단이 정확히 겹치면 그 차단 시도 자체가 `NotFoundException`으로 명시적으로 실패한다(위 "잔여 창" 기록 참고) - 시스템이 스스로 복구하는 것이 아니라, ADMIN이 그 실패를 보고 새로고침 후 재게시된 새 공유를 다시 조회해 명시적으로 재시도해야 한다. 사소한 잔여 창이라 이번에는 새 Admin API 없이 그대로 기록만 남겼다.

3. **그룹 C - "지금 상태가 ACTIVE다"만으로는 부족하고, "언제부터 ACTIVE였는지"까지 봐야 한다.**
   - 흐름: 사용자가 Google 계정 연결 해제(Disconnect) 버튼을 누르는 순간, 그 이전에 이미 시작해 둔 재인증(OAuth) 시도나 공유 파일 확인 요청이 뒤늦게 도착할 수 있다. 상태만 보면 "지금 ACTIVE"로 보일 수 있어(재연결까지 끝났다면) 그 뒤늦은 요청을 새 요청처럼 착각하기 쉽다.
   - 기법: "연결 인가 세대"(Connection Epoch)라는 숫자를 하나 더 둔다 - 이 숫자는 오직 연결 해제(Disconnect)할 때만 올라간다(평소 Token 자동 갱신으로는 절대 안 올라간다). 재인증을 시작하는 순간 이 숫자를 적어 두고, 실제로 저장/활성화하기 직전에 지금 저장된 숫자와 다시 비교한다 - 다르면 "그사이 뭔가 있었다"는 뜻이므로 거부한다. 마치 회의실 예약표에 "몇 번째로 바뀐 예약인지" 도장을 찍어 두고, 나중에 도착한 사람이 옛 도장을 들고 오면 돌려보내는 것과 같다.
   - 작은 예시: `source_connections.connection_epoch`(V011) - `disconnect()`가 `bumpConnectionEpoch()`를 호출하고, `GoogleDriveOAuthService.commitCredential()`과 `EffectivePermissionService.decideShared()`가 각각 저장해 둔 값과 지금 값을 비교한다.
   - 한계/테스트: `SourceTokenConcurrencyTest`(재사용) + `GoogleDriveOAuthServiceTest.handleCallbackFailsClosedWhenTheConnectionEpochAdvancedAfterAuthorizationStarted` + `FileMetadataDiscoveryServiceTest.aDisconnectReconnectCycleDuringTheLiveCheckExcludesTheItemEvenThoughStatusReadsActiveAgain` - 다만 이 Epoch는 "연결 해제/재연결"만 감지하며, Google 쪽 파일 권한 자체가 바뀌는 것은 별도의 Live 재확인(`verifyCurrentMetadata`)이 담당한다(둘은 서로 다른 방어선이다). 또한 이번에 "신원이 한 번도 확인되지 않은(Legacy) 연결은 공유를 열어주지 않는다"는 검사(`SOURCE_IDENTITY_UNVERIFIED`)도 같은 자리에 추가했다 - `FileMetadataDiscoveryServiceTest.anUnverifiedLegacyProviderIdentityCannotGrantSharedDiscoveryUntilVerifiedBindingIsEstablished`.

**M10B 후속 교정(2026-09-15) - "잠긴 문이 있다"와 "그 문 뒤 값을 다시 읽었다"는 다른 이야기다**

- 흐름: 위 그룹 C가 도입한 `connection_epoch`를 두 번 연속 Disconnect(예: 사용자가 버튼을 두 번 누르거나, 탭을 두 개 열어 둔 경우)가 겹쳐서 건드리면 무슨 일이 생기는지가 이번 교정의 주제다. `disconnect()`는 이 값을 올리기 전에 이미 한 번 그 Source 행을 읽어 뒀는데(Method 맨 위), 그 뒤 실제로 행을 잠그는 절차(Token 삭제 경로)는 "잠갔다"는 사실만 확인해줄 뿐 "잠근 순간의 진짜 값"을 그 먼저 읽어 둔 Java 객체에 다시 넣어주지 않는다. 그래서 두 Disconnect가 겹치면 둘 다 "잠그기 전에 읽어 둔 낡은 값"에 각자 +1만 계산해, 실제로는 2번 올라야 할 값이 1번만 올라간 것처럼 보였다.
- 기법: "Java 객체의 값에 +1"이 아니라, DB에게 "너의 지금 값에 +1을 해줘"라고 그대로 위임한다(`UPDATE ... SET connection_epoch = connection_epoch + 1`) - 이러면 Java 쪽이 무엇을 기억하고 있는지와 전혀 무관하게, 항상 그 순간 DB에 실제로 적힌 값을 기준으로 계산된다. 마치 "내가 마지막으로 본 은행 잔액에 만원을 더해서 새로 적어라"가 아니라 "지금 통장에 있는 잔액에 만원을 더해라"라고 은행에 직접 시키는 것과 같다 - 내가 마지막으로 본 잔액이 이미 낡았어도 상관없다.
- 작은 예시: `SourceConnectionJpaRepository.incrementConnectionEpoch(id)`(원자적 증가) + `findCurrentConnectionEpoch(id)`(그 결과를 다시 읽음) + `SourceConnectionEntity.syncConnectionEpoch(그 값)`(Java 객체에 동기화) - `SourceConnectionService.disconnect()`가 이 세 단계를 **Token 삭제 직후, 다른 어떤 필드도 아직 건드리기 전에** 수행한다. 개발 중 이 순서를 반대로 했더니(Status/TokenRef를 먼저 바꾼 뒤 이 세 단계를 나중에 실행) Hibernate가 "다른 변경사항을 마저 반영해야겠다"며 그 원자적 증가보다 먼저 낡은 값을 저장해 버려 똑같은 결함이 재현됐다 - 순서 자체가 교정의 핵심이었다.
- 한계/테스트: `SourceTokenConcurrencyTest.twoOverlappingDisconnectsBothAdvanceTheConnectionEpochWithoutLosingEitherIncrement`(실제 2-Thread로 겹치는 Disconnect를 재현, `CountDownLatch`로 정확한 시점에 멈춰 세운다 - Sleep 없음) - 이 교정은 `connection_epoch` 하나에만 적용되고, 실제 Google 계정으로 정확히 이 순간에 두 번 Disconnect를 누르는 것은 검증하지 않았다(Mock/Testcontainers 기반 재현이다).

**M16C(2026-09-16) - "documentId"와 "shareId"는 이름이 비슷해도 완전히 다른 것이다**

- 흐름: B(수신자)가 문서 검색 화면에서 "SDV 다운로드"를 누르면, 그 요청은 `documentId`가 아니라 `shareId`(그 파일을 지금 보여준 바로 그 공유의 ID)로 나가야 한다. 같은 문서라도 옛날에 철회된 공유와 지금 살아있는 공유는 ID가 다르므로, `documentId`로 추측해서 부르면 이미 죽은 공유를 부르거나(실패) 반대로 위험할 수 있다.
- 기법: Backend가 검색 결과(`RagFileItem`) 안에 "지금 이 항목을 실제로 통과시킨 공유의 ID"(`shareId`)를 함께 실어 보낸다 - Client는 이 값을 그대로 다운로드 Endpoint에 전달할 뿐, 스스로 계산/추측하지 않는다. 그리고 Client가 이 값을 위조하거나 낡은 값을 보내도, 다운로드 Endpoint(`SharedFileDownloadService`, M10C에서 이미 구현됨)가 매번 서버에서 다시 전체 인가를 재확인하므로 이 값은 어디까지나 "UI가 버튼을 보여줄지 말지 정하는 힌트"일 뿐 인가 자체가 아니다("UI action information is only a hint; the download endpoint remains authoritative").
- 작은 예시: `RagFileItem(documentId=100, shareId=57, allowedActions=["VIEW","DOWNLOAD"])` - Frontend는 `documentId`로 화면에 목록을 그리고, 다운로드 버튼을 누르면 `GET /api/shares/57/download`(정확히 `shareId`)를 부른다. `FileMetadataDiscoveryService.toItem(document, live, share)`가 이 결합을 만든다 - `document.getId()`(documentId)와 `share.getId()`(shareId)를 절대 같은 변수에 담지 않는다.
- 한계/테스트: `FileMetadataDiscoveryServiceTest.shareIdAndAllowedActionsAreBoundToTheExactSurvivingShareNotAnotherOne`(서로 다른 두 공유의 shareId/allowedActions가 정확히 자신의 파일에만 붙는지 교차 확인) - 다만 이 값 자체는 "힌트"이므로, 실제 다운로드 성공/실패는 여전히 M10C의 실제 재인가 로직에 달려 있다(이번 Slice가 그 로직을 검증한 것은 아니다).
